# 本地可视化知识库系统 — 计划文档（v0.3 定稿）

> 状态：**需求已定稿**，进入开发准备（v0.4 = API 契约 + DDL + 部署脚本骨架）
> 版本：v0.3
>
> **v0.3 变更（决策全部锁定）**：
> 1. Embedding **默认走云端**（OpenAI 兼容 embedding API）；本地 bge-m3 作为隐私备选方案保留（无 GPU，仅特殊场景启用）；
> 2. 数据**统一由管理员在服务器上传**；不给租户发上传类密钥（预留 `ingest` 密钥设计，未来需要远程补数据时再开放）；
> 3. 其余默认：OCR 默认关闭（遇到扫描件再开）；提供 OpenAI 兼容 `/chat/completions` 聚合端点；仅管理员一个 Web 账号；规模按中等设计（每租户 ≤ 数千文档，Qdrant + Neo4j 足够）；
> 4. **对接方式**新增通俗说明（§3.8）：三种接口都做，优先级 = ②OpenAI 兼容聚合端点 + ①REST 检索接口 优先，③MCP 第二期接入。

## 1. 项目概述

### 1.1 背景与目标

构建一个**部署在单台 Windows 机器上的本地可视化知识库系统**：

- 管理员通过 Web 界面**上传文档**（PDF / Word / Markdown / TXT / PPT / Excel 等）；
- 系统自动完成：**文档解析 → 文本切分 → 向量化 → 知识图谱构建**；
- 前端以**数据管理 + 可视化**为核心（**不是问答聊天前端**）：文档、切分块、知识图谱、密钥、审计日志直接查看与编辑；
- 对外提供**检索接口（REST / OpenAI 兼容 / MCP）**，供**多台远程电脑上的云端大模型 / AI Agent** 调用本地知识来生成回答；
- **多租户权限隔离（核心）**：每台电脑持独立 API 密钥，**只能检索到分配给它的知识库数据**，高峰约 **10 台并发**调用。

### 1.2 多租户业务模型

```
                    ┌─────────────────────────────────────────┐
                    │  本地知识库系统（单机 Windows，管理员维护）    │
                    │                                         │
                    │  知识库 A ──┐                           │
                    │  知识库 B ──┼── 绑定 ─ 密钥 #1 ──▶ 电脑 1   │
                    │  知识库 C ──┘                           │
                    │                                         │
                    │  知识库 D ──┐                           │
                    │  知识库 E ──┼── 绑定 ─ 密钥 #2 ──▶ 电脑 2   │
                    │            └─ ...                      │
                    │  知识库 F ── 绑定 ─ 密钥 #10 ──▶ 电脑 10   │
                    └─────────────────────────────────────────┘
```

- 每个"电脑/客户端"是一个**租户**，拥有自己的一个或多个知识库；
- 每个租户下发**独立 API 密钥**，密钥绑定其知识库集合；
- 任何检索请求由服务端强制按密钥注入知识库过滤，**互不可见、不可越权**；
- **数据由管理员统一上传维护**，租户只通过接口检索（不开放远程上传）；
- 数据（文档/向量/图谱）统一存在本机，回答生成由各租户自己的云端大模型完成。

### 1.3 核心原则

| 原则 | 说明 |
|---|---|
| 本地数据为主 | 文档、切分块、向量、图谱全部落本地；回答生成由各租户的云端大模型完成 |
| 检索与生成解耦 | 本地只做"知识管理与检索"，是知识提供方；各电脑调用各自的云端大模型 |
| 权限即过滤 | 所有检索请求在**服务端强制注入密钥对应的知识库过滤**，客户端无法绕过 |
| 图谱可人工修正 | LLM 自动抽取实体/关系后，管理员可在前端确认、修改、删除 |
| 即时更新 | 上传/编辑后增量入库，检索结果立即可用，无需重建索引 |

### 1.4 非目标（明确不做）

- ❌ 不做面向终端用户的问答聊天前端（对话由各租户自己的大模型侧负责）；
- ❌ 不做大模型训练/微调；
- ❌ 不做云端 SaaS 部署（本机部署，远程电脑仅通过接口调用）；
- ❌ 不做租户自助上传/租户 Web 登录（仅管理员维护数据）。

### 2.2 技术选型（定稿）

| 模块 | 定案 | 说明 |
|---|---|---|
| 后端 | Python 3.11 + FastAPI + Uvicorn | 单进程托管 REST + 前端静态文件 |
| 前端 | Vue 3 + TypeScript + Element Plus + AntV G6 | 打包后由 FastAPI 直接托管 |
| 关系库 | **PostgreSQL 16** | 元数据、权限、审计 |
| 向量库 | **Qdrant**（Windows 原生 exe 或 Docker） | 单 collection + `kb_id` payload 过滤 |
| 图数据库 | **Neo4j Community**（Windows 服务或 Docker） | 实体 <5 万规模足够 |
| Embedding | **云端 OpenAI 兼容 embedding API（默认）** | 无 GPU 提速；本地 bge-m3 仅作隐私备选 |
| 大模型（生成） | 各租户自配云端 OpenAI 兼容端点 | DeepSeek/通义/智谱/OpenAI/Kimi 均兼容 |
| 任务队列 | 进程内 asyncio 队列 + tasks 表 | 无 Redis，Windows 友好 |
| 文档解析 | pdfplumber / pypdf / python-docx / markdown-it / openpyxl | OCR（PaddleOCR）默认关 |
| 部署 | 路线 A：Docker Desktop(WSL2)；路线 B：原生 Windows | 见 §2.4 |

### 2.3 核心数据流

**写入流（管理员上传 → 入库）：**

```
上传文档 → 任务队列（进程内）
        → ① 解析（文本/表格抽取；OCR 可选）
        → ② 切分（chunk + 元数据：来源文档/页码/标题）
        → ③ 向量化（云端 embedding，payload 带 kb_id/doc_id）
        → ④ 图谱抽取（LLM 抽取实体/关系 → Neo4j，标记未确认）
        → ⑤ 更新文档状态
```

**读取流（远程电脑调用）：**

```
电脑上的大模型/Agent（持密钥#N）→ 检索请求
        → 服务端鉴权：解析出该密钥授权的 kb_ids
        → 向量检索（强制 kb 过滤）
        → 图谱检索（种子实体 + 邻域，同样 kb 过滤）
        → 结果融合 → 返回 chunks + 子图（带来源）
        → 该电脑的云端大模型基于结果生成回答
```

### 2.4 Windows 单机部署方案

**路线 A：Docker Desktop（WSL2）— 推荐**
- `docker-compose.yml` 编排：postgres / qdrant / neo4j / backend（含前端静态文件）；
- 前提：Windows 10/11 64 位 + WSL2 + 虚拟化开启。

**路线 B：原生 Windows 安装（无法用 Docker 时）**
- PostgreSQL 官方安装包（服务方式）；Qdrant 官方 `qdrant.exe`；Neo4j 官方 Windows 服务（需 JRE/JDK 17）；
- 后端：Python 虚拟环境 + Uvicorn（NSSM 注册服务）；任务队列用进程内 asyncio，无 Redis。

**Windows/无 GPU 注意事项**
- Embedding 走云端 API，本机无向量化算力负担；
- OCR（PaddleOCR）CPU 慢，默认关闭，仅对扫描件手动开启；
- 文件存储用本地磁盘目录；备份 = PG dump + Qdrant snapshot + Neo4j dump + 文件目录拷贝。

## 3. 功能需求详述

### 3.1 文档管理与解析

- **上传**：管理员 Web 上传（拖拽/批量）；PDF、DOCX、MD、TXT、HTML、PPTX、XLSX；上传时指定**归属知识库**（即归属租户）。
- **任务状态**：`排队中 / 解析中 / 切分中 / 向量化中 / 图谱抽取中 / 完成 / 失败(含错误)`，前端实时可见。
- **解析**：文本类直接抽取；表格保留结构（转 Markdown/JSON）；扫描 PDF 可选 OCR（默认关）。
- **元数据**：文件名、大小、类型、页数、归属知识库、标签；可编辑、可删除（级联清理向量+图谱）。
- **重解析**：修改参数后对单个文档重新入库。

### 3.2 文本切分（Chunking）

- 按知识库配置 `chunk_size / overlap / 分隔符`；保留标题层级、页码、表格标记到 chunk 元数据。
- 前端可查看、编辑、合并、拆分 chunk；编辑后该 chunk 增量重新向量化。

### 3.3 向量化与索引

- Embedding **默认云端 OpenAI 兼容 API**（定稿）；切换本地 bge-m3 作为隐私备选（需全量重建）。
- 单 collection，payload：`kb_id, doc_id, chunk_id, doc_name, page, seq`；
- 检索**必带 `kb_id ∈ 授权集合` 过滤**（权限核心，见 §3.7）。

### 3.4 知识图谱构建

- **自动抽取**：LLM 从文档/切分块抽取实体（人/组织/产品/术语/事件/指标）与关系，结构化 JSON 写入 Neo4j；
- **去重/溯源**：同名实体合并、关系去重、实体挂接来源文档与切分块；
- **人工校准**：前端 G6 画布新增/编辑/删除/合并节点与边；`verified` 标记；即时生效；
- **成本控制**：图谱抽取可配置开关与限流。

### 3.5 混合检索（向量 + 图谱）

- 向量检索 Top-K（可配 K/阈值）；
- 图谱检索：查询实体命中后沿关系扩展 1~2 跳，取子图及关联文本块；
- 融合排序：两路去重合并，可选 rerank（默认关，按需开）；
- 输出：chunks + 子图 + 来源引用（文档名/页码）。

### 3.6 数据可视化前端（非问答）

页面清单见 §6。核心：文档管理、切分块编辑、图谱画布编辑、检索调试台（验证用，非对话）、密钥管理、审计日志。

### 3.7 密钥与多租户权限（核心）

- **管理端账号**：管理员登录 Web UI（用户名/密码），负责上传数据、建知识库、发密钥。
- **API 密钥（每台电脑一个或多个）**：
  - 密钥绑定：`1..N 个知识库`（即该租户的数据范围）；
  - 密钥类型（定稿）：
    - `search`：只读检索（默认给电脑用）；
    - `full`：检索 + 管理（仅管理员自用）；
    - `ingest`：预留（未来如需租户远程上传再开放）；
  - 可设过期、一键吊销、用量统计（次数/返回条数）。
- **强制过滤（防越权）**：检索请求 → 服务端解析密钥 → 得到授权 `kb_ids` → **服务端拼接向量库 payload 过滤 + 图库 Cypher `WHERE n.kb_id IN $allowed`**，客户端传参不可扩大范围；
- **审计**：每次检索记录密钥、租户、时间、查询、返回条数、IP。

### 3.8 对外接口（给远程电脑上的大模型调用）— 对接方式说明

> 先解释"对接方式"是什么：你的本地系统是**知识仓库**，10 台电脑上的 AI 程序要"带钥匙进仓库查资料"。但"怎么查"有三种接法，区别在于 **谁负责写"调用知识库"的代码**：

| 方式 | 是什么 | 谁写调用逻辑 | 适合场景 |
|---|---|---|---|
| ① **REST 检索接口** | 普通 HTTP 接口：程序发请求（带密钥+问题）→ 返回命中的知识片段（JSON） | **电脑端的程序自己写**（curl / 代码 / Postman） | 你们自研的系统、任何能发 HTTP 的程序；实现简单、便于测试 |
| ② **OpenAI 兼容聚合端点** | 一个**长得和 OpenAI 一模一样**的接口：发问题 → 本地自动检索 + 调云端模型 → **直接返回回答** | 调用方**完全不用写**，当普通 OpenAI API 用 | 用现成 AI 平台（Dify / Coze / 各种支持 OpenAI 接口的工具），或希望"一句话拿答案" |
| ③ **MCP 服务** | AI 工具标准协议：支持 MCP 的 AI 客户端（Claude / Cursor / Dify 等）**自动调用**知识库工具，把结果带进对话 | **AI 客户端自动管理** | 用现成 AI 客户端/Agent 框架，希望 AI 自己决定何时查资料 |

**决策（定稿）：三种都做，分优先级**
1. **第一优先**：② OpenAI 兼容聚合端点 + ① REST 检索接口 —— 开发简单、任何调用方都能用、便于验收测试；
2. **第二优先**：③ MCP —— 等确认电脑侧实际用的客户端/平台后再接入（协议成熟，对接现成工具最省事）。

**接口清单**
- `POST /api/v1/knowledge/search`：混合检索（语义+图谱），返回 chunks + 子图（方式①）；
- `POST /api/v1/knowledge/graph/query`：图谱定向查询（方式①）；
- `POST /api/v1/chat/completions`：OpenAI 兼容聚合端点，本机检索 + 调该租户云端模型生成回答（方式②，定稿提供）；
- MCP 工具：`search_knowledge_base` / `get_graph_subgraph` / `list_documents`（方式③，第二期）；
- 统一 `Authorization: Bearer <密钥>` 鉴权。

### 3.9 系统管理

- 云端模型配置（Base URL / API Key / 模型名，支持多厂商并存，每个租户可选自己的厂商）；
- Embedding 配置（默认云端；本地 bge-m3 备选）；切分与解析参数；图谱抽取开关与限流；
- 备份/恢复；审计日志。

## 4. 数据模型设计（核心表）

```
users(id, username, password_hash, role, created_at)
knowledge_bases(id, name, description, owner_user_id,
                chunk_size, chunk_overlap, embedding_model,
                graph_extraction_enabled, created_at)
documents(id, kb_id, filename, file_path, file_size, file_type,
          status, parse_params, error_msg, page_count, created_at, updated_at)
chunks(id, kb_id, doc_id, seq, content, metadata(jsonb),
       embedding_status, created_at, updated_at)
entities(id, kb_id, name, type, properties(jsonb),
         source_doc_id, verified, created_at, updated_at)
relations(id, kb_id, source_entity_id, target_entity_id,
          relation_type, properties(jsonb), source_doc_id,
          verified, created_at, updated_at)
api_keys(id, user_id, name, key_hash, key_type,
         allowed_kb_ids(jsonb), expires_at, revoked,
         last_used_at, created_at)
audit_logs(id, api_key_id, user_id, action, query,
           result_summary(jsonb), ip, created_at)
tasks(id, type, status, progress, params(jsonb), result(jsonb),
      created_at, updated_at)
```

**向量 payload**：`{ kb_id, doc_id, chunk_id, doc_name, page, seq }`
**图谱节点/边属性**：`{ kb_id, name, type, verified, source_doc_id, ... }`（全部带 `kb_id` —— 图谱侧权限过滤基础）

## 5. 对外 API 设计（示例）

### 5.1 混合检索（方式①）

```
POST /api/v1/knowledge/search
Authorization: Bearer <电脑的密钥>
{ "query": "设备的日常维护周期是多久？", "top_k": 8, "graph_depth": 1 }
→ 200
{
  "chunks": [ { "chunk_id": "c1", "content": "...", "score": 0.86,
                "kb_id": "kb3", "doc_name": "维护手册.pdf", "page": 5 } ],
  "graph": { "entities": [...], "relations": [...], "paths": [...] },
  "permission_scope": { "kb_ids": ["kb3", "kb4"] }   // 本次实际生效范围
}
```

### 5.2 图谱定向查询（方式①）

```
POST /api/v1/knowledge/graph/query
{ "entity": "维护周期", "relation_types": ["属于","依赖"], "depth": 2 }
```

### 5.3 OpenAI 兼容聚合端点（方式②，定稿）

```
POST /api/v1/chat/completions
Authorization: Bearer <电脑的密钥>
{ "model": "<该租户配置的模型名>", "messages": [{"role":"user","content":"..."}] }
→ 与 OpenAI 完全相同的响应格式
// 服务端：用该密钥授权的知识库检索 → 组装 system prompt + context → 调该租户云端模型 → 返回
```

### 5.4 权限过滤实现要点（防绕过）

1. 服务端从 Header 解析密钥 → 查库得 `allowed_kb_ids`；
2. 向量检索：`filter = {"must": [{"key": "kb_id", "match": {"any": allowed_kb_ids}}]}`，**忽略客户端传入的任何 kb 参数**；
3. 图谱检索：Cypher 首行 `WHERE n.kb_id IN $allowed`；
4. 密钥吊销即时失效（缓存短 TTL）；密钥只存哈希；
5. 全部请求落审计。

## 9. 性能与并发设计（10 并发，无 GPU）

- **检索链路**：Qdrant 单机可支撑千级 QPS 量级，10 并发向量检索 + Neo4j 1~2 跳遍历无压力；瓶颈不在检索本身。
- **瓶颈分析**：
  | 环节 | 说明 | 对策 |
  |---|---|---|
  | 检索（向量/图谱） | 毫秒级，10 并发轻松 | 无需特殊处理 |
  | 图谱抽取（LLM） | 入库时批量任务 | 队列限流、分批、可关 |
  | **向量化** | **走云端 API（定稿）**，本机无负担 | 云端 embedding 吞吐远高于本地 CPU；入库按批提交、失败重试 |
  | rerank | 默认关闭 | 按需开或改用 LLM 打分 |
  | 云端大模型生成 | 在每台电脑侧/云端，不占本机 | 本机只做检索 + 转发，天然卸载 |
- **结论**：10 并发检索完全可行；云端 embedding 方案下本机无算力瓶颈，唯一依赖是云端 API 的可用性与额度（需配置好 Key 与限流重试）。
